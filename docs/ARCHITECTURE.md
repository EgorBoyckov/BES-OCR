# Архитектура BES OCR

## 1. Стек

Python 3.11 · PySide6 (GUI) · PyMuPDF + pdfplumber (PDF) · Tesseract 5 / pytesseract (OCR)
· OpenCV + NumPy + Pillow (обработка изображений) · img2table (детекция таблиц на сканах) · python-docx (генерация DOCX)

## 2. Структура каталогов

```
bes_ocr/
  __main__.py            точка входа (python -m bes_ocr)
  app.py                  запуск QApplication + MainWindow
  logging_setup.py        настройка логирования (файл + in-memory буфер для GUI)
  config/
    settings.py           Settings: языки OCR, DPI, число воркеров, пути
  core/
    models.py             модель документа (Document/Page/Block/...)
    errors.py             исключения, PageError
    pdf_source.py         открытие PDF, рендер страниц, извлечение текстового слоя/изображений
    text_layer.py         оценка качества текстового слоя страницы
    ocr_engine.py          препроцессинг + Tesseract (слова, строки, bbox, confidence; OCR отдельной ячейки)
    font_metrics.py       метрики глифов Times New Roman: кегль по ширине/высоте слова OCR
    color_marks.py        вырезание цветных печатей/подписей со скана (PNG с прозрачностью)
    layout_analysis.py    сборка слов/строк в параграфы/заголовки/списки, двухколоночные блоки
    table_detection.py    поиск таблиц (pdfplumber для текстового слоя, img2table для сканов) + объединённые ячейки
    page_processor.py     обработка одной страницы (оркестрация всех модулей выше)
    pipeline.py           обработка документа целиком: страницы, колонтитулы, сборка Document
    docx_writer.py        генерация .docx из модели Document
  jobs/
    worker.py             фоновый воркер (QThread) с прогрессом/отменой, работает поверх pipeline
  gui/
    main_window.py        главное окно
    widgets.py             область drag&drop, панель прогресса, журнал
tests/
  conftest.py             генерация тестовых PDF-фикстур (reportlab/PyMuPDF)
  test_*.py               unit- и end-to-end тесты
docs/                     документация
packaging/                PyInstaller spec, скелет .deb
```

## 3. Модель документа (`core/models.py`)

Внутреннее представление не зависит ни от PDF, ни от DOCX:

* `Document` — список `Page`, метаданные.
* `Page` — список `Block` в порядке чтения + `page_break_after`.
* `Block` (union): `Heading`, `Paragraph` (список `Run` с bold/italic/size/цвет),
  `ListItem` (уровень, маркер/номер), `Table` (список `TableRow` → `TableCell`
  с `row_span`/`col_span`, список `Block` внутри ячейки), `ImageBlock`
  (байты изображения + размер + подпись), `HeaderFooter` (текст, номер страницы).
  Каждый `Block` несёт `BoxStyle`: bbox, выравнивание, отступы, номер страницы
  источника — это и есть "восстановленная структура" из п.4 ТЗ.

Это разделение — ключевое архитектурное решение: `page_processor.py` строит
модель независимо от способа получения текста (текстовый слой или OCR),
а `docx_writer.py` не знает вообще ничего о PDF/OCR — только о модели.
Это позволяет протестировать генерацию DOCX без PDF и наоборот.

### 3.1. Геометрия страницы DOCX

Для визуального сходства с оригиналом размер страницы и поля DOCX
вычисляются из модели (`docx_writer._compute_page_geometry`), а не берутся
по умолчанию (иначе получился бы Letter с полями в 1 дюйм независимо от
того, что было в PDF — систематически ломает перенос строк и пропорции
таблиц даже при верно распознанном содержимом): размер страницы — из
`Page.width_pt/height_pt`, поля — по 10-му/90-му процентилю фактических
левых/правых краёв текстовых блоков (единичный выброс вроде таблицы у
самого края не должен задавать поле для всей страницы). По той же причине
`Table.col_widths_pt` (ширины столбцов из `table_detection.py`, по
не-объединённым по горизонтали ячейкам) передаются в реальные ширины
столбцов python-docx, а не оставляются равномерными, и `ImageBlock`
вставляется в размере исходного bbox, а не растягивается на всю ширину
страницы.

Той же причине подчинён размер шрифта текста внутри ячеек таблицы:
`page_processor.py` передаёт в `detect_tables_pdfplumber`/
`detect_tables_img2table` медианный размер шрифта тела страницы
(`font_size_pt`), и он записывается в `Run.size_pt` ячейки, а
`docx_writer._write_table` применяет его к `run.font.size`. Раньше текст
ячеек не нёс размер шрифта вовсе и получал стиль Word по умолчанию
(~11pt) независимо от реального (часто более мелкого) шрифта плотных
таблиц бланков — при ширине столбцов, взятой из настоящей геометрии
документа, это давало намного больше переносов строк, чем в оригинале, и
раздувало документ лишними страницами (измерено на реальном документе:
2 страницы источника → 3 страницы результата; после исправления — 2 → 2).

### 3.2. Вёрстка "один в один"

Цель конвертации — не только правильный текст, но и та же вёрстка:
кегль, выравнивание, переносы строк и вертикальное положение каждой строки.

* **Кегль OCR-текста** (`font_metrics.py`, `layout_analysis.normalize_ocr_words`).
  Высота рамки слова зависит от того, есть ли в нём выносные элементы:
  "программа" и "компоненты" одного кегля дают рамки, различающиеся почти
  в полтора раза. Раньше кегль брался как высота × 0.8, отсюда разный
  размер почти у каждого слова. Теперь кегль оценивается по строке целиком:
  по "чернильной" ширине слов (метрики Times New Roman с боковыми полями
  глифов), а если длинных слов нет — по высоте с учётом глифов. Оценки
  страницы кластеризуются и округляются до типовых кеглей (9, 10, 12, 14…).
  Полужирное начертание определяется по относительной толщине штриха
  (`ocr_engine.stroke_width_px`) среди строк того же кегля.
* **Абзацы и выравнивание** (`layout_analysis._ParagraphBuilder`).
  Выравнивание считается относительно измеренных границ текста страницы,
  а не краёв листа. Перенос между строками либо естественный (следующее
  слово не поместилось бы), и тогда его заново сделает Word, либо
  принудительный. Принудительный перенос у текста по центру или справа
  сохраняется как разрыв строки (шапка "Приложение 1 / к договору…"),
  у текста по левому краю или по ширине он завершает абзац. В модели
  хранится геометрия абзаца: базовая линия первой строки, шаг строк,
  левая и правая границы, отступ первой строки. Для OCR ещё подбирается
  межбуквенный интервал: текст в Times New Roman выбранного кегля занимает
  ту же ширину, что в оригинале (±3.5%), поэтому Word переносит строки
  в тех же местах.
* **Две колонки** (`layout_analysis._find_column_bands`). Граница колонок —
  интервал по x, свободный от слов во всех строках полосы одновременно
  (строке только с одной колонкой он не мешает). Требования к полосе:
  не меньше трёх строк с текстом по обе стороны, обе колонки шире
  четверти страницы, одна из колонок выровнена по коридору. Полоса
  охватывает только строки между первой и последней такой строкой.
  Результат — таблица-раскладка без рамок (`Table.borderless`).
* **Таблицы на сканах**. img2table находит только сетку, а каждая ячейка
  распознаётся отдельно (`OcrEngine.recognize_region`, psm 6). При
  распознавании всей страницы Tesseract терял "№", номера строк и
  заголовки узких граф. В ячейках сохраняются переносы строк оригинала,
  выравнивание по горизонтали и вертикали, высоты строк и измеренные
  поля ячеек. Таблица может заходить на поля, как в оригинале.
* **Печати и подписи** (`color_marks.py`). Цветные отметки вырезаются
  в PNG с прозрачным фоном и ставятся плавающими изображениями
  (`ImageBlock.floating`, `wp:anchor` за текстом) в исходные координаты.
  Из растра для OCR они стираются.
* **Вертикальные позиции** (`docx_writer._Flow`). У каждого абзаца
  точный межстрочный интервал, равный измеренному шагу. Отступ перед
  абзацем вычисляется так, чтобы базовая линия в Word совпала с базовой
  линией оригинала, от того места, где закончился предыдущий блок
  (включая таблицу). Положение базовой линии внутри строки с точным
  интервалом L (0.805·L от верха строки) откалибровано по рендеру
  LibreOffice.
  Разрыв страницы задаётся свойством первого абзаца страницы, а не
  отдельным абзацем.

## 4. Конвейер обработки (per-page decision)

```
PDF (PyMuPDF)
  → для каждой страницы:
      1. text_layer.assess(page)         → есть ли пригодный текстовый слой
      2. если слой хороший:  извлечь текст+шрифты (PyMuPDF), таблицы (pdfplumber)
         если слоя нет/плохой: растрировать страницу (DPI по config),
             ocr_engine.recognize() → слова+bbox+confidence,
             table_detection через img2table (см. docs/RESEARCH.md, п.5.1) на растре
      3. layout_analysis: слова/строки → параграфы/заголовки/списки/выравнивание
      4. обнаружение изображений (PyMuPDF: встроенные растры; для сканов —
         страница уже является изображением, поэтому шаг 4 неактуален)
      5. рукописный текст: если Tesseract даёt низкий confidence на блоке и
         эвристика (высокая доля "мусорных" слов) — блок сохраняется как
         изображение вместо текста (п.3 ТЗ)
      6. сборка Page (модель)
  → pipeline: сведение повторяющихся верхних/нижних строк на страницах в
      HeaderFooter, нумерация страниц, разрывы страниц
  → docx_writer: Document → .docx
  → верификация результата (docx открывается, счётчики блоков/таблиц)
```

Обработка страницы обёрнута в try/except на уровне `page_processor`: ошибка
одной страницы превращает её в placeholder-блок с сообщением об ошибке и не
прерывает документ (п.13 ТЗ).

## 5. Производительность и большие документы

* Страницы обрабатываются **потоково**: рендер/OCR одной страницы, немедленная
  сборка блоков, освобождение растра — весь документ разом в памяти не
  держится.
* `ThreadPoolExecutor` (по умолчанию `min(4, cpu_count)`) распараллеливает
  OCR/анализ страниц; результаты собираются по номеру страницы, чтобы порядок
  в DOCX не зависел от порядка завершения потоков.
* Фоновая обработка выполняется в `QThread` (`jobs/worker.py`), GUI получает
  прогресс через сигналы Qt (`page_done(i, total)`, `stage_changed(str)`) —
  интерфейс не блокируется.
* Поддержка отмены: `CancellationToken`, проверяется между страницами и внутри
  цикла OCR по страницам.
* **Измерено в этой среде разработки** (не Astra Linux — см. `docs/RESEARCH.md`,
  4 потока обработки, DPI по умолчанию 300): скан без текстового слоя без
  таблиц/шума, 60 страниц — 44 с (≈0.74 с/страницу), пиковая память процесса
  ≈1.4 ГБ. На тесте `tests/test_pipeline.py::test_large_document_100_plus_pages`
  (105 страниц с текстовым слоем, без OCR) — ≈10 с. Обработка не зависает и не
  деградирует по мере роста числа страниц (проверено вплоть до 105 страниц) —
  подтверждает, что исправление `OMP_THREAD_LIMIT=1` (см. `bes_ocr/__init__.py`)
  по-прежнему устраняет многоминутные зависания на сканах при включённом
  многопоточном постраничном OCR. Память растёт с числом страниц (все `Page`,
  включая байты вложенных `ImageBlock`, остаются в объекте `Document` до
  записи DOCX) — на многократно больших документах (500+ страниц) стоит
  ожидать пропорционально больше памяти; отдельно не измерялось.

## 6. Обработка ошибок

`core/errors.py`: `PdfOpenError`, `PageProcessingError`, `DocxWriteError`,
`DiskSpaceError`. Все ошибки страниц собираются в `Document.warnings` и
отображаются в журнале GUI, не прерывая весь прогон (кроме фатальных:
файл не открывается, диск заполнен).

## 7. Логирование

`logging_setup.py` настраивает стандартный `logging` на два handler'а: файл
(`~/.local/share/bes-ocr/logs/`) и `QtLogHandler`, кладущий записи в
потокобезопасную очередь, которую GUI отображает в панели "Журнал". В лог не
пишется содержимое документа пользователя — только метаданные (номер
страницы, тип блока, коды ошибок), см. `docs/LIMITATIONS.md` и п.17 ТЗ.

## 8. Тестирование

Фикстуры (`tests/conftest.py`) генерируются программно (reportlab + PyMuPDF),
без бинарных PDF в репозитории — воспроизводимо и без внешних файлов.
Уровни тестов: unit (по каждому core-модулю), end-to-end (PDF → DOCX →
проверка структуры результата через python-docx), smoke GUI (offscreen Qt
platform). Подробности в `docs/TESTING.md`.

## 9. Упаковка

PyInstaller `--onedir` + `.deb`, `Depends: tesseract-ocr, tesseract-ocr-rus,
tesseract-ocr-eng`. Подробности — `docs/BUILD.md`.

## 10. Идеи на будущее из scan2docx-architecture

Пользователь принёс независимый архитектурный документ гипотетической
системы scan2docx (IR на pydantic, VLM через vLLM, PP-DocLayout/TableFormer,
FastAPI/Docker, замкнутый цикл визуальной валидации с repair loop) как
источник идей для развития BES OCR — не как техзадание на copy-paste. Это
принципиально другой масштаб системы (микросервисы, GPU, внешние тяжёлые
модели), несовместимый с требованием проекта работать полностью локально и
офлайн на Astra Linux без GPU (см. `CLAUDE.md`). Ниже — что из него реально
применимо к текущему масштабу проекта, что уже сделано под его влиянием, и
что сознательно не переносится.

**Уже применено (этот раздел документа):**
* `bes_ocr/devtools/validate.py` — постраничный SSIM + проверка числа
  страниц через LibreOffice headless, ровно то, чем весь этот сеанс
  сравнение делалось вручную (см. `docs/TESTING.md`). Взято из раздела
  «visual validation» scan2docx-документа, но без scikit-image/Hungarian-
  сопоставления блоков — минимальная версия, которая ловит реальные
  регрессии этого проекта (раздутие на лишние страницы, испорченная
  геометрия), не многотысячестрочная система.
* **Частично: интервалы между блоками** (раздел 7.2/8.3 scan2docx — «зазоры
  между абзацами через space_before»). Обнаружено и исправлено: у модели
  `Paragraph.space_before_pt` существовал с самого начала, но нигде не
  заполнялся и не читался — реальный вертикальный зазор между блоками
  (измеренный по расстоянию между строками в оригинале) отбрасывался, и
  каждый абзац получал жёстко зашитые в шаблон python-docx/Word значения
  по умолчанию (`space after` 10pt + межстрочный множитель 1.15×,
  `docDefaults` в `styles.xml`) — независимо от того, насколько плотно
  расположен текст в оригинале. Теперь `layout_analysis.build_blocks`
  заполняет `space_before_pt` реальным зазором, а `docx_writer` отключает
  автоматический "space after"/1.15× и использует его. На реальном
  документе (через `bes_ocr/devtools/validate.py`): mean SSIM 0.638 → 0.643,
  число страниц не изменилось (было и осталось 2/2) — то же раздутие,
  что раньше проявлялось резко (3 страницы вместо 2 из-за шрифта ячеек
  таблицы), здесь копится тише, но по той же причине.
  Симуляция переноса строк по метрикам конкретного шрифта (раздел 8.3
  scan2docx целиком) не реализована — это гораздо более тяжёлая задача
  (нужны метрики fontTools, эталонные ширины символов, итеративный подбор
  кегля/трекинга), и здесь она не потребовалась: точное совпадение
  зазоров между блоками само по себе уже устраняет основной источник
  систематического раздувания, обнаруженный в этом проекте на практике.

**Кандидаты на будущее (в порядке убывания пользы/усилий для этого проекта):**
* **Реализовано (см. 3.2):** двухколоночные блоки по коридору, свободному
  во всех строках полосы, а также подбор кегля и межбуквенного интервала
  по метрикам шрифта.
* ~~**Whitespace-анализ колонок с разбиением страницы на полосы**~~ (раздел
  7.1: устойчивые вертикальные просветы шире `k × медианная высота
  строки`, в духе Breuel — и, что важнее, СНАЧАЛА разбиение страницы на
  горизонтальные полосы по естественным границам вроде заголовков/таблиц,
  и только потом поиск колонок внутри каждой полосы отдельно). Опробовано
  дважды и оба раза отклонено — см. `docs/LIMITATIONS.md`,
  «Многоколоночная вёрстка», где подробно описана вторая попытка (якорные
  строки с широким внутристрочным разрывом + классификация слов по
  x-координате) и её конкретная причина отказа: без предварительного
  разбиения на полосы эвристика "от первого якоря до конца страницы"
  ошибочно захватывает случай, когда на одной странице два независимых
  двухколоночных блока, и раздувает документ (проверено: 2 страницы → 3,
  `visual_score` 0.643 → 0.142). Именно разбиения на полосы не хватило в
  обеих попытках — это по-прежнему единственная предложенная здесь идея,
  прямо нацеленная на известный дефект, но следующая попытка должна
  начинаться с полос, а не пытаться улучшить формулу поиска разрыва.
* **`block_iou`/`text_cer` метрики поверх текущего SSIM-сравнения** —
  показали бы, *что именно* разошлось (не просто "страница непохожа"), но
  требуют сопоставления блоков и текстового слоя из рендера LibreOffice —
  заметно больше кода ради диагностики, а не поведения приложения.

**Сознательно не переносится:**
* **VLM (Qwen-VL/dots.ocr через vLLM).** Требует GPU и внешний процесс —
  прямо противоречит офлайн/CPU-цели проекта на Astra Linux. Tesseract уже
  выбран как основной движок по итогам оценки PaddleOCR (`docs/RESEARCH.md`,
  раздел 3.1) именно по офлайн-критерию.
* **Отдельная pydantic-схема IR, entry points, реестр плагинов, FastAPI/
  Docker/очередь задач.** Оправдано для системы с несколькими
  движками-конкурентами на выбор и внешними потребителями API. Здесь один
  движок (Tesseract), один потребитель (десктопный GUI) — `core/models.py`
  уже играет роль IR ровно в том объёме, который нужен (см. CLAUDE.md:
  модель не знает о PDF/OCR/DOCX), без сопутствующей инфраструктуры.
* **TableFormer/SLANeXt вместо img2table.** img2table уже даёт то, что
  требуется по ТЗ (реальные редактируемые таблицы Word с объединёнными
  ячейками), работает на CPU офлайн и проверен на реальном документе.
