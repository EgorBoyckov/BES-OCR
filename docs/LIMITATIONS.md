# Известные ограничения

* **Проверка на реальной Astra Linux 1.7 не выполнялась в этой сессии.**
  Разработка и тестирование велись на Ubuntu 24.04 (ближайшее практическое
  приближение — см. `docs/RESEARCH.md`). Перед боевым использованием
  необходима проверка на целевом стенде (`docs/BUILD.md`, раздел 3).
* **Обнаружение таблиц на сканах без каких-либо линий.** По умолчанию
  `detect_tables_img2table` ищет таблицы, образованные линиями
  (`borderless_tables=False`) — img2table умеет находить и полностью
  безграничные таблицы по выравниванию текста, но эвристика менее надёжна
  и в текущей версии сознательно отключена, чтобы не плодить ложные
  таблицы из обычных многоколоночных блоков текста (см. пункт про
  многоколоночную вёрстку ниже). Проверено на реальном документе: включение
  `borderless_tables=True` действительно добавляет ложные таблицы — помимо
  настоящих таблиц по линиям, оно ошибочно распознаёт как "таблицу" и
  нумерованный список ("Перечень отчетных документов"), и двухколоночный
  блок реквизитов ("Университет:"/"Профильная организация:"), которые
  таблицами не являются. Решение оставить выключенным подтверждено этим
  экспериментом, а не только теоретическим опасением.
* **Рукописный текст.** Не распознаётся как текст в принципе (это не
  требовалось ТЗ). Есть два уровня fallback на изображение: если "мусорны"
  большинство слов страницы — вся страница сохраняется как изображение
  (`is_likely_handwriting_or_noise`); если мусор локален (типичный случай —
  печать/подпись поверх части печатного текста), `find_noise_regions`
  находит именно этот локальный участок по плотности коротких/невнятных
  слов (доверие OCR одного слова здесь ненадёжно само по себе — короткие
  обрывки росчерка подписи Tesseract часто "читает" уверенно) и сохраняет
  только его как изображение, не трогая остальной текст страницы. Более
  тонкая гранулярность (отдельные символы/мазки внутри найденного участка)
  не реализована — весь найденный прямоугольник целиком становится
  изображением.
* **Многоколоночная вёрстка.** Двухколоночные блоки (например, реквизиты
  сторон) распознаются и передаются таблицей-раскладкой без рамок (см.
  `docs/ARCHITECTURE.md`, 3.2). Это третий подход. Первые два (разрыв
  внутри отдельных строк, "от якорной строки до конца страницы")
  отклонены из-за регрессий. Сейчас граница колонок — интервал, свободный
  от слов во всех строках полосы, а границы полосы ограничены строками,
  которые на этот интервал опираются. Ограничения: поддерживаются только
  две колонки. Газетная вёрстка на всю страницу (текст перетекает из
  колонки в колонку) передаётся как таблица из двух ячеек, а не как
  колонки раздела Word.
* **Шрифт текста со сканов.** OCR не знает гарнитуру, поэтому текст
  набирается Times New Roman (`Settings.default_font_name`), а кегль
  подбирается по метрикам Times. Для документов, набранных рубленым
  шрифтом (Arial и т.п.), кегль подбирается по ширине, строки
  переносятся в тех же местах, но гарнитура отличается от оригинала.
  Определение гарнитуры — возможное развитие.
* **Вертикальное положение строк.** Положение базовой линии при точном
  межстрочном интервале откалибровано по рендеру LibreOffice (целевая
  платформа Astra Linux). В MS Word оно может отличаться на доли пункта
  на строку. В Word это не проверялось.
* **Печати и подписи.** Как изображения отделяются только цветные
  (синие/фиолетовые) отметки. Чёрно-белые печати и подписи на
  монохромных сканах по-прежнему ищутся эвристикой `find_noise_regions`
  и сохраняются как плавающие изображения участка. Текст, полностью
  закрытый печатью, может распознаваться с ошибками.
* **Таблицы на сканах.** В ячейках сохраняются переносы строк оригинала
  (явные разрывы строк). Так ячейка выглядит как в оригинале, но при
  редактировании текста в ячейке эти разрывы останутся.
* **Нумерация списков.** Пункты используют стили Word "List Number".
  Отдельные списки в документе продолжают общую нумерацию, а не
  начинаются с 1.
* **Многоуровневые списки.** DOCX-списки используют стандартные стили
  `List Bullet`/`List Number`; вложенность списков передаётся только через
  отступ (`left_indent`), а не через полноценные многоуровневые
  нумерованные списки Word (`numPr` с уровнями).
* **Изображения на страницах OCR.** Встроенные растровые изображения
  извлекаются только для страниц с текстовым слоем (`PdfSource.extract_images`).
  Для отсканированных страниц вся страница уже обрабатывается как единое
  изображение/OCR-источник, отдельные вложенные картинки на сканах не
  выделяются как самостоятельные `ImageBlock`.
* **Визуальное сравнение PDF/DOCX.** Помимо структурных assert'ов над
  `python-docx` (см. `docs/TESTING.md`), теперь есть отдельный дев-инструмент
  `bes_ocr/devtools/validate.py` — объективное постраничное сравнение через
  SSIM + совпадение числа страниц (не часть поставляемого приложения,
  требует LibreOffice только на машине разработчика). Он НЕ сопоставляет
  отдельные блоки/текст между исходником и результатом (`block_iou`,
  `text_cer` из вдохновившего документа scan2docx-architecture) — только
  общую раскладку страницы целиком. Более тонкое сравнение (что именно
  разъехалось, а не просто "страница стала непохожа") остаётся возможным
  развитием проекта.
* **EasyOCR/PaddleOCR как альтернативный движок** упомянуты в исследовании
  как вариант для будущего повышения точности, но не реализованы — сохранён
  только интерфейс `OcrEngine`, допускающий замену бэкенда.
