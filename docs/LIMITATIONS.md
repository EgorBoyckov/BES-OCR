# Известные ограничения

* **Проверка на реальной Astra Linux 1.7 не выполнялась в этой сессии.**
  Разработка и тестирование велись на Ubuntu 24.04 (ближайшее практическое
  приближение — см. `docs/RESEARCH.md`). Перед боевым использованием
  необходима проверка на целевом стенде (`docs/BUILD.md`, раздел 3).
* **Обнаружение таблиц на сканах без каких-либо линий.** По умолчанию
  `detect_tables_img2table` ищет таблицы, образованные линиями
  (`borderless_tables=False`) — img2table умеет находить и полностью
  безграничные таблицы по выравниванию текста, но эвристика менее надёжна
  и в текущей версии сознательно отключена, чтобы не плодить ложные
  таблицы из обычных многоколоночных блоков текста (см. пункт про
  многоколоночную вёрстку ниже). Проверено на реальном документе: включение
  `borderless_tables=True` действительно добавляет ложные таблицы — помимо
  настоящих таблиц по линиям, оно ошибочно распознаёт как "таблицу" и
  нумерованный список ("Перечень отчетных документов"), и двухколоночный
  блок реквизитов ("Университет:"/"Профильная организация:"), которые
  таблицами не являются. Решение оставить выключенным подтверждено этим
  экспериментом, а не только теоретическим опасением.
* **Рукописный текст.** Не распознаётся как текст в принципе (это не
  требовалось ТЗ). Есть два уровня fallback на изображение: если "мусорны"
  большинство слов страницы — вся страница сохраняется как изображение
  (`is_likely_handwriting_or_noise`); если мусор локален (типичный случай —
  печать/подпись поверх части печатного текста), `find_noise_regions`
  находит именно этот локальный участок по плотности коротких/невнятных
  слов (доверие OCR одного слова здесь ненадёжно само по себе — короткие
  обрывки росчерка подписи Tesseract часто "читает" уверенно) и сохраняет
  только его как изображение, не трогая остальной текст страницы. Более
  тонкая гранулярность (отдельные символы/мазки внутри найденного участка)
  не реализована — весь найденный прямоугольник целиком становится
  изображением.
* **Многоколоночная вёрстка (газетный стиль, двухколоночные блоки
  реквизитов).** Текущий layout-анализ группирует строки по вертикали и не
  выполняет отдельного определения колонок — строки из левой и правой
  колонки одного визуального ряда сливаются в одну строку слева направо, а
  не читаются "сначала вся левая колонка, потом вся правая". Такая
  двухколоночная детекция была реализована и опробована на реальном
  документе (поиск устойчивого разрыва между колонками по совокупности
  начальных x-координат слов, с приоритетом разрыва ближе к центру
  страницы), но геометрия реальных сканов оказалась для неё недостаточно
  регулярной: положение "лучшего" разрыва нестабильно менялось в
  зависимости от того, сколько строк накоплено в пробеге, и в части
  случаев результат получался ХУЖЕ исходного (слово ошибочно отрывалось от
  своей же колонки). Решение убрано как ненадёжное, а не оставлено
  включённым с известными ложными срабатываниями — учитывая приоритет
  проекта на точности, лучше сохранить предсказуемое (хоть и не идеальное
  по порядку чтения) построчное поведение, чем непредсказуемо иногда
  портить текст.

  **Вторая попытка (более поздняя сессия) — тоже отклонена, но нашла более
  точную причину.** Гипотеза была в том, что первую попытку подводила
  именно ПОСТЕПЕННАЯ природа поиска разрыва; версия, которая ищет разрыв
  один раз по всему пробегу целиком (вместо накопления построчно), тоже не
  сработала на реальном документе — но по другой, куда более
  фундаментальной причине, обнаруженной только эмпирическим разбором:
  `words_to_lines` группирует слова по вертикали БЕЗ понятия о колонках,
  поэтому строки одной визуальной "полосы" часто уже содержат слова
  ОБЕИХ колонок вперемешку внутри одного объекта `LayoutLine` ещё до
  всякой попытки их разделить. Если у левой и правой колонки разное число
  строк текста (а это почти всегда так, если тексты сторон разной длины),
  то на БОЛЬШИНСТВЕ строк реально присутствует текст только одной из
  колонок — внутристрочный разрыв на такой строке в принципе не может
  указывать на границу колонок, потому что второй колонки в этой строке
  просто нет. Рабочим сигналом оказались не разрывы на каждой строке, а
  несколько строк-"якорей" (например, строка с обоими заголовками
  "Университет:"/"Профильная организация:" на одной высоте) с явным
  широким разрывом, чьи позиции согласуются между собой — эта техника
  успешно восстановила связный читаемый текст **для одного конкретного
  блока** на реальном документе (проверено вручную). Но при полном
  end-to-end прогоне на реальном PDF из двух страниц оказалось, что у
  ДОКУМЕНТА ЕСТЬ ДВА таких двухколоночных блока (по одному на страницу), и
  допущение "область действия — от первого якоря до конца страницы"
  (разумное для одного блока в самом низу бланка) даёт неверный результат,
  когда после блока на странице есть что-то ещё или обнаруживается второй,
  отдельный блок такого рода: страница 0, где эта эвристика тоже
  сработала, в результате раздулась (документ вырос с 2 до 3 страниц,
  `visual_score` через `bes_ocr/devtools/validate.py` упал с 0.643 до
  0.142) — то есть тот же класс регрессии "иногда результат хуже исходного",
  что и в первой попытке, просто с другим триггером. Отклонено по тем же
  причинам, что и раньше. Остаётся кандидатом на будущую работу, но со
  следующим уточнением задачи: нужна не просто более стабильная формула
  поиска разрыва, а полноценное разбиение страницы на "полосы"
  (по признакам, не зависящим от того, что именно ищем — например, по
  заголовкам/таблицам как естественным границам) ДО применения
  двухколоночной эвристики к каждой полосе по отдельности, а не одна
  эвристика "от якоря до конца страницы" на всю страницу целиком.
* **Многоуровневые списки.** DOCX-списки используют стандартные стили
  `List Bullet`/`List Number`; вложенность списков передаётся только через
  отступ (`left_indent`), а не через полноценные многоуровневые
  нумерованные списки Word (`numPr` с уровнями).
* **Изображения на страницах OCR.** Встроенные растровые изображения
  извлекаются только для страниц с текстовым слоем (`PdfSource.extract_images`).
  Для отсканированных страниц вся страница уже обрабатывается как единое
  изображение/OCR-источник, отдельные вложенные картинки на сканах не
  выделяются как самостоятельные `ImageBlock`.
* **Визуальное сравнение PDF/DOCX.** Помимо структурных assert'ов над
  `python-docx` (см. `docs/TESTING.md`), теперь есть отдельный дев-инструмент
  `bes_ocr/devtools/validate.py` — объективное постраничное сравнение через
  SSIM + совпадение числа страниц (не часть поставляемого приложения,
  требует LibreOffice только на машине разработчика). Он НЕ сопоставляет
  отдельные блоки/текст между исходником и результатом (`block_iou`,
  `text_cer` из вдохновившего документа scan2docx-architecture) — только
  общую раскладку страницы целиком. Более тонкое сравнение (что именно
  разъехалось, а не просто "страница стала непохожа") остаётся возможным
  развитием проекта.
* **EasyOCR/PaddleOCR как альтернативный движок** упомянуты в исследовании
  как вариант для будущего повышения точности, но не реализованы — сохранён
  только интерфейс `OcrEngine`, допускающий замену бэкенда.
