# Исследование окружения и технологий

Этот документ фиксирует результаты исследования, предшествовавшего разработке
BES OCR, и обоснование выбора технологий.

## 1. Целевая платформа — Astra Linux Special Edition 1.7

Astra Linux SE 1.7 — сертифицированный дистрибутив на базе Debian 10 (buster),
с частично изолированным набором репозиториев ("Astra Linux Directory") и
длительным циклом обновлений пакетов. Ключевые следствия для архитектуры:

* **Системный Python не пригоден как единственная опора.** В репозиториях SE 1.7
  доступен Python 3.7 (иногда 3.5 в базовом составе), тогда как современные
  версии PySide6, OpenCV и PyMuPDF требуют Python ≥3.9. Вывод: приложение
  должно распространяться с **собственным изолированным окружением**
  (виртуальное окружение с отдельным интерпретатором Python 3.11, либо
  PyInstaller-сборка в один каталог/файл), не полагаясь на системный `python3`.
* **Отсутствие гарантированного доступа в интернет.** Astra Linux часто
  разворачивается в закрытом контуре. Все зависимости (включая языковые
  модели Tesseract) должны быть включены в поставку — установка "по требованию"
  из pip/apt во время работы приложения недопустима.
* **Графическое окружение.** Astra Linux SE поддерживает Fly/MATE на X11 с
  полноценной поддержкой Qt (сама Astra использует Fly, основанную на KDE/Qt).
  Qt-приложения — наиболее нативный выбор GUI-стека для этой платформы.
* **Архитектура.** Основная поставка — x86_64, что совпадает с окружением
  сборки/тестирования.

Так как реальный стенд с Astra Linux 1.7 в этой сессии недоступен, проверка
выполнена на Ubuntu 24.04 (тот же класс: Linux, glibc, X11/Qt, Python 3.11) —
как ближайшем практическом приближении. Перед боевым развёртыванием
необходима финальная проверка собранного пакета на реальном стенде Astra
Linux 1.7 (см. `docs/BUILD.md`, раздел "Проверка на целевой платформе").

## 2. Язык и GUI-фреймворк

| Вариант | Вывод |
|---|---|
| **PySide6 (Qt6)** | Выбран. Официальный биндинг Qt для Python (LGPL, бесплатный для коммерческого использования), нативный вид в Fly/MATE, встроенные `QThread`/сигналы для фоновых задач без блокировки GUI, `QDrag`/`dropEvent` для drag-and-drop "из коробки". |
| PyQt6/PyQt5 | Технически эквивалентен, но лицензия GPL/коммерческая менее удобна для распространения. |
| Tkinter | Присутствует в stdlib, но не даёт современного вида и качественного drag-and-drop без сторонних хаков. |
| Electron/веб-стек | Требует Node.js/Chromium — тяжелее, хуже вписывается в офлайн-сертифицированную ОС, увеличивает поверхность атаки. |

Итог: **Python 3.11 (в собственном виртуальном окружении/бинарной сборке) + PySide6**.

## 3. OCR-движок

| Вариант | Вывод |
|---|---|
| **Tesseract OCR 5.x (`tesseract-ocr`, пакеты `tesseract-ocr-rus`, `tesseract-ocr-eng`)** | Выбран. Полностью локальный, свободная лицензия (Apache 2.0), пакеты для rus/eng присутствуют в стандартных Debian/Ubuntu репозиториях (совместимо с Astra), зрелая поддержка через `pytesseract`, отдаёт слова с bbox и уровнем уверенности (`image_to_data`) — необходимо для восстановления позиции текста и ячеек таблиц. Проверено в этой среде: `tesseract 5.3.4`, языки `rus`+`eng` распознаются корректно. |
| EasyOCR / PaddleOCR | Более точны на сложных сценах, но требуют PyTorch/PaddlePaddle (сотни МБ, GPU-ориентированы, сложнее гарантированно завести офлайн на сертифицированной ОС). Оставлены как возможное будущее расширение через тот же интерфейс `OCREngine`. |
| Облачные OCR (Google/Yandex/Amazon) | Запрещены требованиями проекта (п. 8 ТЗ) — исключены полностью. |

## 4. Анализ PDF и извлечение текста

| Библиотека | Роль |
|---|---|
| **PyMuPDF (`fitz`)** | Основной доступ к PDF: быстрый рендер страниц в растр (для OCR и предпросмотра), извлечение текстового слоя со шрифтами/размерами/bbox, извлечение встроенных изображений, определение метаданных. |
| **pdfplumber** | Дополнительный анализ текстового слоя: построчная группировка символов, а главное — `page.find_tables()` для обнаружения таблиц по линиям/выравниванию столбцов на страницах с текстовым слоем. |
| **OpenCV** | Обработка растровых страниц: биноризация, определение перекоса (deskew), морфологическое выделение горизонтальных/вертикальных линий таблиц на сканах. |
| **Pillow / NumPy** | Общая работа с изображениями между этапами конвейера. |

## 5. Определение и восстановление таблиц

Главный приоритет проекта. Используется гибридная стратегия:

1. **Текстовый слой есть и таблица образована линиями/выравниванием** →
   `pdfplumber.find_tables()` даёт границы ячеек напрямую; текст ячеек берётся
   из текстового слоя (точный, без ошибок OCR).
2. **Скан / текстового слоя нет** → таблица обнаруживается и распознаётся
   библиотекой **img2table** (MIT, github.com/xavctn/img2table) поверх
   Tesseract — см. ниже, почему выбрана готовая библиотека, а не
   собственная реализация на OpenCV.
3. **Объединённые ячейки** определяются на уровне используемого детектора
   (pdfplumber или img2table) и в обоих случаях приводятся к единому
   внутреннему представлению: обе библиотеки помечают объединённую ячейку
   повторением одного и того же прямоугольника на всех позициях сетки,
   которые она покрывает — код в `table_detection.py` группирует ячейки по
   этому прямоугольнику и создаёт настоящий `cell.merge()` в DOCX.
4. Если таблицу невозможно надёжно разобрать в сетку (нестандартная/сильно
   повреждённая разметка), она вставляется как изображение — это осознанный
   fallback, а не основной путь.

### 5.1. Почему img2table, а не собственный детектор на OpenCV

Первая версия проекта строила сетку таблицы на сканах самостоятельно
(морфологические операции OpenCV, позже — преобразование Хафа для
устойчивости к перекосу). На синтетических тестовых PDF это работало, но
при проверке на реальном пользовательском документе (сшитый/скреплённый
бланк с типичной для сканов лёгкой "волнистостью" строк) результат был
катастрофическим: таблицы либо не находились вовсе, либо соседние строки
ошибочно склеивались в одну ячейку, смешивая данные разных
полей/студентов — то есть ровно то, чего проект должен избегать в первую
очередь. Последовательные попытки исправить это (Хаф вместо морфологии,
расширение окна поиска границы, выравнивание скана перед поиском линий)
показали, что устойчивая к реальным дефектам сканов детекция таблиц —
самостоятельная, нетривиальная инженерная задача, а не просто "чуть
подправить пороги".

img2table — зрелая библиотека, написанная именно для этой задачи:
определение сетки по линиям и по выравниванию (в т.ч. безграничных
таблиц), сопоставление OCR-текста ячейкам, поддержка объединённых ячеек
"из коробки". Работает локально на CPU через тот же Tesseract — без
дополнительных тяжёлых зависимостей, полностью совместима с офлайн-
требованием проекта и Astra Linux. Проверка на реальном документе
подтвердила кардинально более точный результат (корректная сетка вместо
развала таблицы на куски) и оказалась быстрее собственной реализации.
Вывод: нет смысла поддерживать свой менее надёжный детектор, когда
специализированная и проверенная библиотека решает ту же задачу лучше —
код заменён полностью, а не оставлен как fallback.

## 6. Генерация DOCX

| Библиотека | Вывод |
|---|---|
| **python-docx** | Выбрана. Единственная зрелая чистопитоновская библиотека для генерации `.docx` с полным контролем: стили заголовков, выравнивание, отступы, списки (через `numPr`/стили `List Number`/`List Bullet`), таблицы с `cell.merge()`, вставка изображений, колонтитулы и номера страниц через `section.footer`. Не требует установленного MS Word/LibreOffice для генерации. |

## 7. Общий вывод по конвейеру

Классический план "текст → OCR → layout → таблицы → DOCX" подтверждён как
рабочий, но с уточнением: решение "текстовый слой vs OCR" и "pdfplumber vs
OpenCV-сетка для таблиц" принимается **на уровне каждой страницы**, а не
всего документа — так как в одном PDF могут смешиваться текстовые и
сканированные страницы (п. 2 ТЗ). Это отражено в архитектуре
(`docs/ARCHITECTURE.md`, `PageProcessor`).

## 8. Упаковка

* **PyInstaller** (`--onedir`) для сборки автономного каталога с
  Python-интерпретатором и всеми зависимостями (PySide6, PyMuPDF, OpenCV,
  Tesseract вызывается как внешний бинарь `tesseract-ocr`, который
  устанавливается штатным `.deb`-пакетом — он присутствует в базовых
  репозиториях Astra/Debian и не требует специальной сборки).
* Итоговая поставка — `.deb`-пакет, кладущий PyInstaller-сборку в
  `/opt/bes-ocr`, ярлык в меню приложений (`.desktop`-файл) и зависимость от
  `tesseract-ocr`, `tesseract-ocr-rus`, `tesseract-ocr-eng` через `Depends:`.
  Подробности — `docs/BUILD.md`.
